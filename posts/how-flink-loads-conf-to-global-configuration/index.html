Flink 如何读取 flink-conf.yaml 并将其转换为全局可用的 Configuration 对象？
Shen Huanglin
  2026 年 04 月 09 日   2026 年 04 月 27 日
  • Flink

在 Flink 中，将磁盘上的 flink-conf.yaml 转换为内存中全局可用的 Configuration 对象是整个集群启动的第一步，其过程可以拆解为“配置加载 + 对象实例化”两个过程，其中，“配置加载”主要通过 config.sh 脚本实现。

一、config.sh

该脚本是整个 Flink 脚本体系的基石，它负责构建所有 Flink 进程所需的运行时环境。

1.1 执行时机

config.sh 并不是一个由用户直接运行的脚本，而是一个会被其他脚本引入的辅助脚本

  1. 命令行操作：当执行 ./bin/flink run 命令提交作业时，flink 脚本（build-target/bin/flink）会首先引入 config.sh。

  2. 集群启动：执行 ./bin/start-cluster.sh 时，该脚本也会引入 config.sh。

  3. 单进程启动：在 Yarn 或 Kubernetes 环境中，容器启动命令直接调用 jobmanager.sh 或 taskmanager.sh，这些脚本中也会加载 config.sh。

集群启动和单进程启动的区别：

  • 集群启动：通常指通过 Flink 自带的脚本拉起一个完整的分布式环境，通常在 Standalone 模式下使用。

    ① 入口脚本：./bin/start-cluster.sh。

    ② 编排机制：脚本驱动（通过执行入口脚本在当前节点调用 jobmanager.sh 启动 JobManager 进程） + 分布式扇出（调用 config.sh 中的 TMWorkers 函数，它会读取 conf/workers 文件中的主机列表，通过 ssh 或 pdsh 在远程机器逐一调用 taskmanager.sh）。

    ③ 生命周期：集群的生命周期与具体的作业无关，用户可多次提交作业共享集群的资源。

    ④ 资源分配：资源是静态的，若 TaskManager 的 Slot 用完，新作业将无法运行，直到旧作业释放资源。

  • 单进程启动：通常指直接运行 jobmanager.sh 或 taskmanager.sh 启动一个特定的节点，在 Yarn、Kubernetes 或应用模式中是标准做法。

    ① 入口脚本：直接调用 ./bin/jobmanager.sh 或 ./bin/taskmanager.sh。

    ② 编排机制：外部管理驱动（在 K8s 环境中，K8s 控制器负责创建 Pod，并在 Pod 的启动命令中直接运行 jobmanager.sh） + 按需拉起（在 Active 模式下，JobManager 的 ResourceManager 会动态向外部资源管理器申请容器并启动新的 TaskManager 进程）。

    ③ 生命周期：在 Application 模式或 Per-Job 模式下，进程的生命周期与 Job 绑定，一旦 Job 完成，JobManager 和 TaskManager 进程都会被销毁并释放资源。

1.2 核心作用

该脚本的核心职责是“环境标准化”，确保在任意环境下启动时，Flink 进程都能获得一致的参数。

  1. 计算 FLINK_HOME 的绝对路径，防止因相对路径导致的文件找不到问题。

  2. 定位配置文件 flink-conf.yaml 所在的目录。

    注：也是采用“先环境变量后默认值”的原则。

  3. 寻找并校验 JAVA_HOME，确保 JVM 版本符合要求。

  4. 扫描 lib/ 目录，将 Flink 内核 Jar 包、插件和依赖加入到 Classpath 中，通过 constructFlinkClassPath 函数实现。

  5. 根据配置文件计算 JobManager 和 TaskManager 的内存堆大小、GC 策略等，通过 parseResourceParamsAndExportLogs 函数实现。

1.3 export

在 config.sh 脚本中，FLINK_CONF_DIR、FLINK_BIN_DIR、FLINK_LIB_DIR 等都会被执行 export 命令，因为在 Linux Shell 中，普通变量仅在当前脚本进程中可见，export 命令会将该变量放入当前进程的 Environment Block（环境块）中，这是一个由 \0 分隔的连续字符串区域。当启动 JobManager 和 TaskManager 时，以上环境变量字符串会被拷贝到物理内存中，当 Flink 的中第一次尝试通过 System.getenv() 获取变量时，会触发 java.lang.ProcessEnvironment 类的静态初始化

后续直接从不可变快照中返回对应的值，而不再读取操作系统的物理内存。

注：在 Linux Shell 中，界定进程边界的核心是调用脚本的方式，例如使用 source config.sh 或者 . config.sh 则不会创建新进程，而是在当前进程中直接读取并执行脚本的内容，config.sh 中定义的所有变量会直接进入当前进程的变量空间中；如果使用 ./jobmanager.sh 或者 jobmanager.sh start 则会创建新的进程。

二、对象实例化

当 JobManager 和 TaskManager 启动时，会调用 GlobalConfiguration.loadConfiguration() 方法

注：在 JobManager 的启动过程中，该方法的调用发生在其入口类（Entrypoint）中，如 StandaloneSessionClusterEntrypoint（Standalone 模式）、KubernetesSessionClusterEntrypoint（KubernetesSession 模式）、YarnSessionClusterEntrypoint（Yarn 模式），TaskManager 则发生在 TaskManagerRunner 中。

当读取到配置文件后，通过 loadYAMLResource 方法解析 yaml 文件并将键值对保存到 Configuration 类中（本质上是一个经过封装的 Map<String, Object>，用于存储所有的配置项）。当读取完配置文件中的配置项后，Flink 还会将命令行中通过 -D 参数传入的动态属性（Dynamic Properties）合并到 Configuration 中，且命令行参数的优先级更高。

配置对象形成后会传递到集群的所有核心组件。在 JobManager 端，Dispatcher 通过配置对象确定 WebUI 的端口、作业恢复的存储路径等，ResourceManager 利用配置中的资源规格管理和申请 Slot，JobMaster 根据配置决定 Checkpoint 的间隔、重启策略以及生成 ExecutionGraph 的调度行为。在 TaskManager 端，TaskExecutor 根据配置初始化 Memory Manager（划分堆内外内存）和 Netty Stack（配置 Netty 缓冲区），Task Slot 根据配置中的内存比例，将 Managed Memory（托管内存）平分给各个 Slot。其余还有 Actor System、IO Manager、Heartbeat Manager 等关键组件的初始化依赖。

总结

本文梳理了 Flink 1.18 中 config.sh 脚本的执行时机、核心作用以及被 export 的变量如何在 Flink 中被读取到，之后如何转换为 Configuration 对象的过程。
