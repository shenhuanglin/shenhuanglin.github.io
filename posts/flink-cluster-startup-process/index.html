一、EntryPoint

在 Flink 架构中，EntryPoint 是进程启动的起点，而在操作系统层面，EntryPoint 是由外部脚本拉起的。

在 Standalone 模式（不依赖 Yarn/K8s，直接在物理机上运行的集群）下，集群启动的脚本是 flink-dist/src/main/flink-bin/bin/start-cluster.sh

二、JobManager 的启动流程

在 StandaloneSessionClusterEntrypoint 的 main 方法中，通过调用 runClusterEntrypoint → startCluster → runCluster 方法启动集群。

其中调用了 DefaultDispatcherResourceManagerComponentFactory.createSessionComponentFactory(StandaloneResourceManagerFactory.getInstance()) 创建工厂。

工厂内部启动了三个核心组件

  1. Dispatcher：接收作业提交，为每个 Job 创建 JobMaster。
  2. StandaloneResourceManager：Standalone 模式的资源管理器，不主动分配资源，而是等待 TaskManager 主动注册。
  3. WebMonitorEndpoint（REST 服务）：运行在 Dispatcher 中的 REST 服务和 WebUI 的核心承载端点，是 Flink 集群对外提供 HTTP 访问的唯一入口，也是用户、CLI 客户端、第三方监控平台与 Flink 集群交互的核心网关。

此外，还调用了 initializeServices 方法进行核心初始化工作，包括生成 JobManager 唯一标识、创建工作目录、启动 RPC 服务、启动 BLOB 存储服务、高可用服务等。

三、TaskManager 的启动流程

TaskManager 的启动包含三个步骤，分别是构建并启动 TaskManagerRunner、启动 TaskExecutor、完成与 ResourceManager 的连接。

3.1 构建并启动 TaskManagerRunner

在 TaskManagerRunner 的 main 方法中调用 runTaskManager 方法，创建了 TaskManagerRunner，然后执行其 start 方法，在该方法中，首先是调用了 startTaskManagerRunnerServices 方法，创建和启动了多个服务，如高可用服务、心跳服务、监控指标服务等，并创建了 TaskExecutor。

TaskExecutorService 是定义在 TaskManagerRunner 内的接口，其唯一实现是 TaskExecutorToServiceAdapter。

然后执行了 TaskExecutorToServiceAdapter 的 start 方法

其内部主要负责启动 TaskExecutor。

3.2 启动 TaskExecutor

TaskExecutor 是 TaskManager 的核心实现类，即一个 TaskExecutor 代表一个 TaskManager（JVM），它继承自 RpcEndpoint（使其成为一个 RPC 端点，可以接收来自ResourceManager 和 JobMaster 的远程调用），并实现了 TaskExecutorGateway 接口（定义对外暴露的 RPC 方法）。核心职责包括

  1. 向 ResourceManager 注册自身，汇报可用的 Slot 资源。
  2. 接收来自 ResourceManager 的 Slot 分配请求。
  3. 连接 JobMaster，将所需的 Slot 提供给 Job。
  4. 接收 JobMaster 提交的 Task，在对应的 Slot 中以独立线程运行。
  5. 管理 Task 的生命周期，包括启动、取消、Checkpoint 触发等。

一个 Job 可以同时使用多个 TaskExecutor，一个 TaskExecutor 可以同时服务多个 Job（Session 模式下，不同 Job 的 Task 可以运行在同一个 TaskExecutor 的不同 Slot 中）。每个 TaskExecutor 拥有的 Slot 的数量由配置项 taskmanager.numberOfTaskSlots 决定，通常建议其值与机器的 CPU 核数相匹配，避免过度竞争 CPU 资源。默认情况下，同一个 Job 的不同算子子任务可以共享一个 Slot，此时一个 Job 所需的 Slot 总数与该 Job 中的最大并行度相等。

注：每个 TaskManager 是操作系统层面的一个独立进程，该进程内部运行着一个 JVM 实例，意味着每个 TaskManager 拥有独立的堆内存（Heap）和堆外内存（Off-Heap）、独立的垃圾回收（GC）、独立的类加载器（ClassLoader）、独立的线程池。TaskManagerRunner 是 JVM 进程的入口，负责初始化所有服务并启动 TaskExecutor。

执行 start 方法后，触发 RPC 框架调用 TaskExecutor.onStart() 方法，在该方法内部会调用 startTaskExecutorServices 方法启动内部服务

TaskSlotTable 是 TaskManager 中负责资源的核心组件，它维护了一个 Slot 列表，管理每个 Slot 的状态，负责 Slot 的分配和释放。

3.3 完成与 ResourceManager 的连接

LeaderRetrievalService 的 start 方法会保存 ResourceManagerLeaderListener 作为监听器，并创建底层的 Driver，启动对外部系统的监听

之后，LeaderRetrievalService 处于持续监听状态，当底层的 Driver 上报 Leader 变化后，会调用 LeaderRetrievalService 的 notifyLeaderAddress 方法，然后调用 Listener 的 notifyLeaderAddress 方法，再调用 TaskExecutor 的 notifyOfNewResourceManagerLeader → reconnectToResourceManager → tryConnectToResourceManager → connectToResourceManager 方法，构建 TaskExecutorRegistration，其中包含了 TaskExecutor 的 RPC 地址、节点 ID、Slot 数量等，然后创建 TaskExecutorToResourceManagerConnection 并调用 start 方法，内部使用 RetryingRegistration（指数退避重试机制）向 ResourceManager 发送注册 TaskExecutor 的 RPC 调用，RM 将 TaskExecutor 记录后启动心跳监控，返回注册结果。注册成功后，TaskExecutor 会向 RM 发送初始 Slot 报告，其中包含所有 Slot 的状态，并开始对 RM 的心跳监控。

注：ZooKeeper HA 和 Kubernetes HA 模式下的 LeaderRetrievalService 的实现类是 DefaultLeaderRetrievalService。
