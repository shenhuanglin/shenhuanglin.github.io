Flink 集群启动的流程（K8s Session 模式）
Shen Huanglin
  2026 年 05 月 06 日   2026 年 05 月 06 日
  • Flink

一、启动脚本

K8s Session 模式下的启动脚本是 kubernetes-session.sh

二、KubernetesSessionCli

KubernetesSessionCli 是 kubernetes-session.sh 脚本启动的 Java 客户端进程的核心类，负责将 Flink Session 集群部署到 Kubernetes 或重新连接已有的集群。它本身不是集群的一部分，而是一个短暂的客户端工具。

Detached 模式 Attached 模式
配置 默认 -Dexecution.attached=true
客户端生命周期 部署完成后立即退出 保持运行，等待客户端输入
集群生命周期 独立于客户端 客户端退出时集群继续运行或停止
命令 / quit（退出客户端，不停止集群）、stop（退出客户端，同时停止集群）、help（打印帮助信息，继续循环）
适用场景 生产环境长期运行 交互式管理，脚本化停止集群

注：重新连接到已有集群的目的取决于是否使用 Attached 模式，核心是获取已有集群的 ClusterClient 句柄，以便对其进行操作。拿到句柄后，Detached 模式（默认）会打印 WebUI 地址后直接退出，无其他操作，而在 Attached 模式（-Dexecution.attached=true）下会进入交互循环，等待输入 stop 命令停止集群。

三、JobManager 的启动流程

部署 Session 集群的工作由 ClusterDescriptor 接口（K8s 模式下的实现类是 KubernetesClusterDescriptor）的 deploySessionCluster 方法完成，而它又调用了 deployClusterInternal 方法进行部署。

Pod 是 Kubernetes 中的最小可部署单元，是一个或多个容器的集合，这些容器共享一个网络命名空间（IP 地址、端口）和存储卷（Volume），核心特性如下：

特性 说明
共享网络 所有容器共享同一个 IP 地址，容器之间通过 localhost 通信
共享存储 所有容器可以挂载相同的 Volume，共享文件
原子调度 调度的最小单位，所有容器一定运行在同一台物理机上
短暂性 Pod 本身是临时的，被删除后不会自动重建

Pod 内的容器可以分为主容器和 Sidecar 容器（可选），前者负责运行实际业务进程，后者负责日志收集、代理等辅助进程。大多数情况下，一个 Pod 只包含一个主容器。

在 Flink 的 K8s 部署中，Pod 是 JobManager 和 TaskManager 的运行载体，Pod 内的容器启动时会执行 docker-entrypoint.sh，该脚本根据传入的参数执行 kubernetes-jobmanager.sh 或 kubernetes-taskmanager.sh，最终启动对应的 JVM 进程。

JobManager Pod 的启动流程在 CmdJobManagerDecorator 中实现，它会将 command 和 args 写入 Pod 的主容器

K8s 容器实际执行的命令是

Pod 容器的 command 由配置项 kubernetes.entry.path 控制，默认值为 /docker-entrypoint.sh，它是 Flink 官方 Docker 镜像内置的入口脚本，负责接收脚本名称作为参数并调用对应的脚本，它将 bash -c "..." 作为参数接收，并直接 exec 执行，最终调用 kubernetes-jobmanager.sh。

在前面分析 Standalone 模式下 Flink 集群的启动流程的文章中，JM 和 TM 均采用后台守护进程方式（使用 flink-daemon.sh 脚本）启动，而在 K8s 模式下，JM 采用前台方式（使用 flink-console.sh 脚本）启动，原因是在 Kubernetes 中容器的生命周期由其主进程（PID 1）决定，主进程退出，容器就退出，随后 K8s 根据重启策略决定是否重启 Pod。如果使用 flink-daemon.sh 脚本，JVM 进程被放在后台运行，Shell 脚本（容器的主进程）随机退出，K8s 会立即终止整个 Pod，导致 JobManager 被杀死。如果使用 flink-console.sh 脚本，则 JVM 进程通过 exec 成为容器的主进程，容器的生命周期与 JVM 进程完全绑定。

四、TaskManager 的启动流程

在 K8s 模式中，TaskManager 在集群启动时不会预先创建，而是在 Job 提交后，ActiveResourceManager 根据 Slot 需求调用 KubernetesResourceManagerDriver.requestResource() 方法请求资源。KubernetesResourceManagerDriver 是 K8s 层的入口，在它的 requestResource 方法中，调用了 KubernetesTaskManagerFactory.buildTaskManagerKubernetesPod() 方法创建 TaskManager Pod。与 JobManager 类似，在 buildTaskManagerKubernetesPod 方法中，也是通过装饰器的方式创建 TaskManager。

在 kubernetes-taskmanager.sh 脚本中，同样使用 flink-console.sh，使 JVM 进程通过 exec 成为容器的主进程。

Job 结束后，对应的 TaskManager Pod 也会被销毁。

五、与 Standalone 模式的区别

维度 Standalone KubernetesSession
启动入口 start-cluster.sh（Shell 脚本） kubernetes-session.sh → KubernetesSessionCli（Java 客户端）
JM 启动方式 flink-daemon.sh 直接启动 JVM 进程 客户端向 K8s API 提交 Deployment，K8s 调度 Pod
TM 启动方式 start-cluster.sh 预先静态启动 KubernetesResourceManagerDriver 按需动态创建 Pod
RM 类型 StandaloneResourceManager（被动） ActiveResourceManager（主动）
HA 服务 StandaloneHaServices（无 HA） KubernetesLeaderElectionHaServices（ConfigMap）
TM 发现 RM 地址 StandaloneLeaderRetrievalService（固定地址） KubernetesLeaderRetrievalDriver（Watch ConfigMap）

Deployment 是 Kubernetes 中的工作负载控制器，用于声明式的管理 Pod 的生命周期，其价值在于，如果 JobManager Pod 崩溃，会自动重新创建一个新的 JobManager Pod 来替代它，从而保证了 JobManager 的高可用性，裸 Pod 崩溃后不会自动重建。但是 TaskManager 使用的是裸 Pod（即直接创建 Pod），因为 TM 的生命周期由 Flink 的 KubernetesResourceManagerDriver 主动管理，不需要 K8s 的自动重建机制。

被动 RM 和主动 RM 的核心区别在于是否主动管理 TM 的生命周期。被动 RM 是指被动等待 TaskManager 来注册，自己不创建也不销毁 TM，TM 的数量在部署时静态决定。主动 RM 则是根据 SlotManager 声明的资源需求，主动创建 TM（Pod），在 Slot 释放后主动销毁 TM，实现弹性伸缩。

总结

本文梳理了 K8s Session 模式下 Flink 1.18 集群的启动流程，包括启动脚本、KubernetesSessionCli 的作用、JM 的启动流程、TM 的启动流程以及与 Standalone 模式的区别。
