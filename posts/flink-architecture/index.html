Flink 架构
Shen Huanglin
  2026 年 04 月 02 日   2026 年 08 月 23 日
  • Flink

Flink 运行时由两种类型的进程组成：一个 JobManager 和一个或多个 TaskManager。

一、Client

用于准备数据流并将其发送给 JobManager，可以作为 Java 程序的一部分执行，也可以在命令行进程 ./bin/flink run ... 中运行。

二、JobManager

用于负责作业的管理、资源的调度以及任务的协调。包含以下组件

  1. ResourceManager：负责管理所有 TaskManager 提供的 Task Slot（任务槽位，Flink 集群中资源调度的单位）。当 JobMaster 请求资源时，RM 会向外部资源管理器（如 K8s、Yarn）申请新的 TaskManager 或从已有的 TaskManager 中分配槽位。在 Active 模式（K8s、Yarn）下，RM 具有扩缩容权，会动态地根据 SlotRequest 的积压情况增减 TM 的数量，但是在 Standalone 模式下 RM 无法向“外部”申请，如果 Slot 不够，作业会一直处于 CREATED 状态等待，直到有其他作业释放资源。

  2. Dispatcher：接收 Client 提交的 JobGraph 并为每个提交的作业启动一个新的 JobMaster 进程，同时负责运行 Flink WebUI，展示作业状态。在高可用（HA）模式下，还会负责在 JobManager 失败后从存储中恢复作业。

  3. JobMaster：管理作业的生命周期，负责作业从启动、运行到最终完成或失败的全过程。将逻辑上的 JobGraph 转换成可执行的 ExecutionGraph。

    JobGraph：也称为 Logical Graph，根据提交的作业创建有向无环图，顶点是算子，边定义算子的输入/输出关系，并对应于数据流或数据集。

  4. SlotPool：每个 JobMaster 都有自己槽位池，当作业启动时，先查看自己的 SlotPool 中是否有空闲的资源，若没有，则向 ResourceManager 申请，实现了作业内部资源的复用，减少频繁向全局资源管理器申请资源的开销。

  5. Dataflow Graph（ExecutionGraph）：Client 提交的是 JobGraph，JobMaster 将其转换为 ExecutionGraph，其记录了每个并行子任务的状态、部署位置以及中间结果分区，是所有调度决策的数据源。

  6. Scheduler：负责向 ResourceManager 申请 Slot，将 ExecutionGraph 中的任务部署到选定的 TaskManager 上，并进行异常处理，即若某个 Task 挂了，Scheduler 负责根据重启策略决定重启单个 Task 还是整个作业。

  7. Checkpoint Coordinator：负责状态一致性，周期性地向 Source 算子注入 Barrier，接收来自各个 TaskManager 的状态快照确认，当所有 Task 都确认完成后，将该 Checkpoint 标记为完成，并更新 Metadata。

  8. Actor System：Flink 集群的 RPC 通信组件，JobManager 和 TaskManager 以及 Client 之间通信均通过 Actor System 实现，TM 之间的数据传递则是通过 Netty 实现。

至少有一个 JobManager，高可用（HA）设置中有多个 JobManager，其中一个始终是 Leader，其他的是 Standby（备用实例）。

三、TaskManager

TaskManager 也称为 Worker，负责实际执行计算任务并管理本地资源。TaskManager 运行着 Flink 作业分解后产生的 Task（任务），一个 Task 是 JobGraph 中一个算子链的并行实例。至少有一个 TaskManager，其资源调度的最小单位是 Task Slot，Task Slot 的数量表示该 TaskManager 能够并发（Slot 只隔离内存，不隔离 CPU，因此 TM 内的多个 Task 线程共享 CPU，互相竞争）处理的 Task 的数量。TaskManager 由以下几个部分组成

  1. TaskExecutor：TaskManager 的核心实现类，负责任务生命周期管理（接收来自 JobMaster 的部署请求，启动、停止、取消 Task）、状态汇报（维护任务的运行状态并定期向 JobMaster 汇报）和心跳机制（与 ResourceManager 和 JobMaster 保持心跳）。
  2. Task Slot：TM 内部的资源单位，实现资源隔离（一个 TM 可以有多个 Slot，每个 Slot 平分 TM 的托管内存（Managed Memory），Flink 1.18 中，Slot 可以根据作业的具体需求动态申请不同的 CPU 和内存规格，而非均分）和并发控制。
  3. Network Stack：基于 Netty 实现数据的序列化、反序列化和跨 TM 传输，核心组件是 ResultPartition（上游 Task 产出数据的缓冲区） 和 InputGate（下游 Task 接收数据的入口），是 Shuffle 操作的底层实现。通过 Credit-based Flow Control 实现精细化的流量控制，防止下游过载引发的反压，通过 Zero-Copy 减少内存拷贝，提高大吞吐量场景下的传输效率。
  4. Memory Manager：管理 TM 的内存。为了避免 JVM GC 导致的停顿，Flink 的内存模型分为 Framework Heap/Off-heap（Flink 框架自身使用的内存）、Task Heap/Off-heap（用户算子使用的内存）、Managed Memory（专用于 RocksDB/ForSt 状态后端、批处理排序和缓存）、Network Memory（用于网络传输的缓冲区）。
  5. IO Manager：负责磁盘操作，包括溢写（当内存不足时，将中间结果写到磁盘）和状态本地缓存（在存算分离架构下，负责管理本地磁盘上的状态缓存）。
  6. Library Cache Manager：负责为每个作业下载并缓存所需的 Jar 包，利用 UserCodeClassLoader 确保不同作业之间的类库不冲突。
  7. Broadcast Variable Manager：专门管理广播流或数据集，确保同一节点上的不同 Task 可以高效共享同一份广播数据，无需每个 Task 单独存一份，节约内存。

Job 和 Task 的区别：

  • Job是一个完整的、独立的 Flink 数据处理程序，包含整个数据处理流水线（Source → Transformations → Sink），生命周期从用户执行 execute 方法开始，到所有 Task 成功完成或失败/取消结束。
  • Task 是 Job 分解后的最小执行单元，是 JobGraph 中一个算子链的并行实例，代表一个具体的、在 Slot 中运行的线程，执行特定算子链的计算逻辑，生命周期从被 JobManager 调度到 TaskManager 的 Slot 上启动开始，到其负责的计算处理完毕（或失败）结束。一个 Job 可以包含多个 Task。

四、算子链优化

在满足以下所有条件时自动触发，将多个算子的 Subtask 合并成一个 Task（算子链）执行，能够减少线程间的切换、缓冲的开销，并且在减少延迟的同时增加整体吞吐量。

  1. 相邻算子
  2. 相同并行度
  3. Forward 数据传输模式：最关键的条件。上游算子产生的数据必须能够以 Forward 的方式传输给下游算子，即
    • 点对点、一对一传输：上游算子的每个 Subtask 产生的输出数据，必须只发送给下游算子的一个特定的 Subtask。
    • 无重分区：数据传输不需要根据 key（如 keyBy()）、 Round-Robin（如 rebalance()）或 Broadcast 等规则进行重新分发。数据的分区在上下游 Subtask 之间的对应关系是固定的。

五、Task Slot 和资源

每个 TaskManager（Worker）都是一个 JVM 进程，可以在单独的线程中执行一个或多个 Subtask（多个 Subtask 在同一个线程内顺序执行）。Task Slot（至少一个）用于控制一个 TaskManager 中能够并发执行的 Task 的数量。 每个 Task Slot 代表 TaskManager 中资源的固定子集，使得各个 Task 之间不会竞争托管内存。

默认情况下，Flink 允许 Subtask 共享 Slot，仅要求来自于同一个作业，不要求必须是同一个 Task，所以一个 Slot 可以持有整个作业管道。具有以下优点

  1. 一个 Job 所需的 Task Slot 数量和作业中的最大并行度（所有算子的并行度的最大值）恰好相同**，无需计算程序总共包含多少个 Task，即同一个 Task 的不同 Subtask 必须放在不同的 Slot 中，而不同 Task 的 Subtask 可以放在同一个 Slot 中。
  2. 更好地利用资源。如果没有 Slot 共享，非密集 Subtask 将阻塞和密集型 Subtask 同样多的资源。

补充：

  • 非密集型 Subtask 是指低 CPU/内存消耗，仅做简单转换或数据转发，典型算子包括 Source、Map、Filter。
  • 密集型 Subtask 是指高 CPU/内存消耗，需要处理复杂计算或维护大量状态，典型算子包括 Window、Aggregate、Join。
  • Flink 资源隔离的单位是 Task Slot，每个 Slot 被分配固定大小的资源，当禁用 Slot 共享时，每个 Subtask 独占一个 Slot，Slot 资源按最重量级算子配置。

六、Flink 的部署模式

在 Flink 的分布式架构中，部署模式决定了集群的生命周期、资源隔离程度以及 main 方法在何处执行。

  1. 会话模式（Session Mode）：这是最基础的多租户模式。集群提前启动并长期运行，多个作业共享同一个 JobManager 和资源池。

  2. 单作业模式（Per-Job Mode）：每个任务独享 JobManager 和 TaskManager，资源充分隔离。JobManager 的生命周期和作业的生命周期绑定。

    注：该模式在 Flink 1.15 之后已标记为废弃

  3. 应用模式（Application Mode）：目前 Flink 官方最推荐的部署方式，旨在解决 Per-Job 模式中“客户端负载过重”的问题。

模式 工作机制 优点 缺点
会话模式 预先启动一个固定资源的集群（JobManager 和多个 TaskManager），客户端多次提交作业，所有作业在集群中竞争 Slot 启动快（不需要为每个作业重新申请资源和启动进程）、适合小任务 隔离性差（一个作业挂了可能影响集群的其他作业）、资源竞争
单作业模式 客户端提交作业时，向资源调度器（如 Yarn）申请一套全新的 JobManager 和 TaskManager，作业执行完毕后立即释放资源 强隔离（每个作业有独立的资源，互不干扰） 启动慢（每次都要经历资源申请、进程启动的过程）、客户端压力大（客户端需要解析 JobGraph 并将其发送给 JobManager，消耗客户端大量的 CPU 和带宽）
应用模式 客户端不再本地生成 JobGraph，main() 方法在 JobManager 中执行，JobManager 自行解析图并向 ResourceManager 申请资源 减轻客户端负担、资源利用率高、隔离性好 仅支持 Yarn 和 Kubernetes

总结

本文梳理了 Flink 的架构，包括 Client 的作用、JobManager 的作用与组成部分、TaskManager 的作用与组成部分、算子链优化的作用和条件、Task Slot 的作用与共享 Slot 的优点、Flink 的三种部署模式的工作机制与优缺点。
