Flink 中的 StreamGraph 是如何生成的？
Shen Huanglin
  2026 年 04 月 17 日   2026 年 06 月 21 日
  • Flink

Flink 中有四种图，分别是 StreamGraph、JobGraph、ExecutionGraph 和 Physical Graph。

StreamGraph（逻辑流图）：根据用户通过 DataStream API 编写的代码生成的 DAG 图，用于表示程序的拓扑结构。

JobGraph（作业图）：将 StreamGraph 中符合条件的节点链接合并成一个任务节点，形成算子链，减少数据交换的开销。

ExecutionGraph（执行图）：JobMaster 按照并行度对 JobGraph 的并行子任务进行拆分，并明确任务间的数据传输方式，是调度层最核心的数据结构。

Physical Graph（物理图）：JobMaster 生成 ExecutionGraph 后，分发给 TaskManager 进行部署。物理图在执行图的基础上，确定了数据存放的位置和收发的具体方式，使 TaskManager 能够对收到的数据进行处理计算。

注：物理图只是具体执行层面的图，不是实际的数据结构。

一、StreamExecutionEnvironment

StreamExecutionEnvironment 提供了一系列方法用于配置流处理程序的执行环境，其职责包括

  1. 构建拓扑：当调用 map、filter、window 等时，StreamExecutionEnvironment 并不执行计算，而是在内部维护一个 List<Transformation<?>> transformations。
  2. 管理配置：持有 ExecutionConfig（控制并行度、容错参数等）和 CheckpointConfig（控制检查点行为）。
  3. 读取数据：从内存、文件或外部数据源（如 Kafka）读取数据，创建 DataStream。
  4. 触发作业：通过调用 execute 方法，将本地构建的 StreamGraph 转换为 JobGraph，并提交给集群的 Dispatcher。

在每个 Flink 程序的最开始，需要先获取执行环境，通常使用 getExecutionEnvironment 方法

该方法优先通过工厂进行决策，根据 resolveFactory 方法的源代码可知，threadLocalContextEnvironmentFactory 具有第一优先级，其用于多线程并发环境，确保每个线程拥有独立的上下文，当通过命令行 ./bin/flink run 提交 Jar 包时，Flink 的 CliFrontend 会预先在当前线程设置 contextEnvironmentFactory。当成功获取到工厂后，就根据配置创建执行环境。如果没有找到任何工厂，则判定当前程序是一个独立的本地程序，会创建一个 LocalStreamEnvironment，它会在当前的 JVM 内部启动一个 MiniCluster，其中包含一个临时的 JobManager 和 TaskManager，通过线程间通信模拟分布式运行。

获取到执行环境后，就要构建 StreamGraph 的数据流入口，即 Source，在 Flink 1.18 版本中，官方推荐使用 StreamExecutionEnvironment 中的 fromSource 方法，该方法用于定义从哪个数据源读取以及使用的 Watermark 策略，然后返回一个 DataStreamSource，作为整个作业的流式拓扑结构的逻辑起点。

注：CliFrontend 是 Flink 命令行工具 ./bin/flink 的核心实现类，负责解析用户输入的命令行参数，构建程序的执行环境，并将程序提交到集群上执行，是用户与 Flink 集群交互的客户端入口。纯客户端进程，不参与 Job 的实际执行，只负责解析命令、与集群通信、提交/管理 Job。./bin/flink 脚本直接启动一个 JVM 进程，将所有参数传递给 CliFrontend 的 main 方法。客户端进程负责以下工作

  • 执行用户的 main 方法，从中提取 Flink 能够理解的数据流图（JobGraph）。
  • 下载用户程序依赖的 Jar 包和资源文件，并上传到集群。
  • 将 JobGraph 通过 REST API 提交到集群的 JobManager 进行调度和执行。
  • 提交完成后，可以断开连接（Detached 模式）或保持连接接收进度报告（Attached 模式）。

客户端进程是重量级的，由此催生了 Application 模式的产生，在该模式下，客户端仅需解析命令行参数，如 ./bin/flink run -t kubernetes-application ./xx.jar，然后将 jar 路径、入口类、动态参数等写入配置，提交给集群，触发创建一个包含作业 Jar 包的 JM Pod，提交完成后立即退出。main 方法在 JM 上执行，JobGraph 在 JM 中生成，不需要客户端下载依赖，执行 main 方法、上传 Jar 包。

二、Transformation

Flink 中，每个会导致“计算”或“数据分发”改变的操作都会生成一个 Transformation，而其中的物理算子（Physical Transformation）则会被添加到 List<Transformation<?>> transformations 中。以 map 操作为例

其内部调用了 transform 方法，而后者又调用了 doTransform 方法，该方法的作用是创建一个新的逻辑节点（Transformation），将其挂载到上游节点之后，并注册到执行环境中

注：

  • DataStream API 用于构建数据流拓扑，其内部保留两个引用，即 StreamExecutionEnvironment 和 Transformation。每个 Transformation 对象包含转换的元数据（名称、并行度、输出类型等）和对输入 Transformation 的引用。
  • 从同一个 StreamExecutionEnvironment 创建的 DataStream 共享同一个 Environment 实例，所有的 DataStream 共享相同的执行配置（如并行度、Checkpoint 设置等），所有的 Transformation 都注册到同一个 Transformation 列表中。
  • 关注点分离原则：DataStream 负责用户 API 层面的逻辑表示，Transformation 负责底层的执行计划表示。
  • 单输入算子是指仅接收一个逻辑输入流的数据的算子。逻辑输入流是指 DataStream API 中定义的上游连接关系，物理输入流是指运行时实际的数据传输路径。
  • execute 方法的执行是真正开始根据 DataStream 数据流拓扑创建 StreamGraph、JobGraph、ExecutionGraph，然后开始接收、处理数据。

Flink 中的 Transformation 可以分为两类，即物理 Transformation 和虚拟 Transformation，其核心区分标准为是否继承 PhysicalTransformation。相比于基类 Transformation，PhysicalTransformation 额外增加了两个能力

  1. setChainingStrategy 方法：控制算子是否可以与相邻算子合并到同一个线程中。
  2. supportsConcurrentExecutionAttempts 方法：控制是否支持并发执行尝试。

在 StreamGraph 中，每个物理 Transformation 都会被转换成一个真实的 StreamNode，对应运行时的一个算子实例，而虚拟 Transformation 直接继承 Transformation，不会转换成 StreamNode。
