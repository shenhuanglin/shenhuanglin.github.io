时间和 Watermark
Shen Huanglin
  2026 年 07 月 20 日   2026 年 07 月 27 日
  • Flink

一、时间语义

Flink 支持三种时间语义，分别是

  1. Event Time（事件时间）：事件实际发生的时间。
  2. Ingestion Time（摄入时间）：数据进入 Source 算子的时间。
  3. Processing Time（处理时间）：数据被具体算子处理时的机器时间。

在实际应用中，事件时间更能反映真实的事件发生顺序，因此从 1.12 版本开始，Flink 将事件时间作为默认的时间语义。

二、Watermark

2.1 定义

在 Flink 中，用于衡量事件时间进展的标记，被称为水位线（Watermark），它是一种用于定义”何时停止等待更早的事件”的机制，用于告知算子“时间已经推进到某个点，不会再有时间戳 $\le$ 该值的数据到达”。在具体实现上，它是由 Source 算子生成的，插入到数据流中的一条携带时间戳的特殊的数据记录。

在 Flink 中，有两个 Watermark 类，分别是

用户实现 WatermarkGenerator 时使用后者，即 onPeriodicEmit 方法中发送的是该 Watermark，Flink 内部将其放入流中传输时，使用前者。算子对 Watermark 的处理规则是，对于不缓冲元素的算子（如 map、filter），直接将接收到的 Watermark 转发给下游，对于缓冲元素的算子（如窗口算子），必须先触发窗口计算、输出结果，然后再发送 Watermark，保证了下游算子收到 Watermark 时，上游已经完成了所有应该触发的计算。

注：这是一个典型的防止循环依赖的分层设计，用户 API 保持轻量，运行时内部实现保持独立，两者通过适配器 WatermarkToDataOutput 在边界处转换。

2.2 作用

在 Flink 中，Watermark 的主要作用包括

  1. 驱动 Event Time 推进：告知下游算子事件时间已经推进到某个点。
  2. 触发窗口计算：EventTimeTrigger 在 Watermark 超过窗口结束时间时触发。
  3. 触发 Event Time Timer：InternalTimerService 在 Watermark 推进时触发注册的定时器。
  4. 处理乱序数据：通过延迟 Watermark 容忍一定程度的乱序。
  5. 多流对齐：多输入算子取所有上游 Watermark 的最小值，保证全局一致性。

窗口用于在无界的流数据中实现有界的计算，它将流切分成有限大小的多个“存储桶”（bucket），每条数据会分发到对应的桶中，当 Watermark 超过窗口结束时间时，就对每个桶中收集的数据进行计算处理，并将窗口关闭销毁。Watermark 触发窗口计算需要满足以下两个条件

  1. Watermark 的时间戳 $\ge$ 窗口的结束时间；
  2. 窗口中有数据。

2.3 生成 Watermark

Flink 中生成 Watermark 的核心是 WatermarkStrategy，它是一个顶层接口，同时继承了 TimestampAssignerSupplier 和 WatermarkGeneratorSupplier 两个接口，前者定义了提取事件时间的方法，后者定义了生成 Watermark 的方法。

其中，WatermarkGenerator 中有两个方法

每接收到一条数据调用一次 onEvent 方法，记录最大事件时间，周期性调用 onPeriodicEmit 方法，发送 Watermark，发送间隔（默认 200 $ms$）由 ExecutionConfig.setAutoWatermarkInterval 方法控制。

注：每条数据都发送 Watermark 会导致性能下降，因为每个 Watermark 都会触发下游计算。

Flink 有以下内置的 WatermarkGenerator

  1. BoundedOutOfOrdernessWatermarks：生产环境中最常用的 Watermark 生成器，允许数据有一定的“延迟”空间，生成的 Watermark 中的时间戳总是滞后于提取到的最大事件时间的一个固定时间间隔。对应的策略是 WatermarkStrategy.forBoundedOutOfOrderness(Duration delay)。假设滞后 3 秒

  2. AscendingTimestampsWatermarks：Watermark 的时间戳总是等于当前提取到的最大事件时间减 1 秒，本质上是 BoundedOutOfOrdernessWatermarks 延迟时间为 0 的一种特殊表现，适用于事件时间严格升序到达的场景。对应的策略是 WatermarkStrategy.forMonotonousTimestamps()。

  3. NoWatermarksGenerator：不生成 Watermark，对应的策略是 WatermarkStrategy.noWatermarks()。

上述策略主要是周期性生成，但是在 Flink 的 WatermarkGenerator 接口定义中，允许两种触发模式，分别是周期性生成和标记生成，后者是指在 onEvent 方法中检测到特殊标记事件时，立即发出 Watermark，不依赖周期性调用，具体的需求逻辑仅需实现 WatermarkGenerator 接口并重写 onEvent 方法和 onPeriodicEmit 方法即可。

2.4 Watermark 处理流程

2.4.1 初始化

在定义 Watermark 时会调用 assignTimestampsAndWatermarks 方法

该方法接收了一个 WatermarkStrategy 参数，将其封装到 TimestampsAndWatermarksTransformation 后，被添加到 transformations 列表中，在生成 StreamGraph 的过程中，会根据 Transformation 类型调用相应的 translateForStreamingInternal 方法。

在 TimestampsAndWatermarksTransformationTranslator 的 translateInternal 方法中，创建了 TimestampsAndWatermarksOperator 并调用其 open 方法。

该方法主要用于生成 timestampAssigner 和 watermarkGenerator，前者用于提取时间戳，后者用于生成 Watermark。而后注册一个定时器，到达指定时间后会调用 onProcessingTime 方法

该方法用于触发生成 Watermark 并再次启动一个定时器。

WatermarkEmitter 是 WatermarkOutput 的实现类，当调用 watermarkGenerator 的 onPeriodicEmit 方法时，实际调用的是 WatermarkEmitter 的 emitWatermark 方法

其保证了 Watermark 的时间戳是单调递增的。

2.4.2 发出 Watermark

对于 BoundedOutOfOrdernessWatermarks，它向下游发送一个 Watermark，时间戳为 maxTimestamp - outOfOrdernessMillis - 1。

2.4.3 下游处理

下游输入的入口通常是 StreamTask.processInput

对于 One-Input Task 则是 StreamOneInputProcessor

调用的实际是 AbstractStreamTaskNetworkInput 的 emitNext 方法，核心逻辑是

反序列化出来的统一类型是 StreamElement，他可能是 StreamRecord、Watermark、WatermarkStatus、LatencyMarker，然后进入 AbstractStreamTaskNetworkInput.processElement 进行分发

当下游收到 Watermark 时，先交给 StatusWatermarkValve。算子可能有多个上游并行子任务（多个 Input Channel），每个 Channel 独立发送 Watermark，算子必须读取所有 Active & Aligned Channel 的最小值才能向下游推进。以上逻辑通过 StatusWatermarkValve 实现，它负责

  1. 记录每个输入 Channel 的 Watermark ACTIVE/IDLE 状态；
  2. 从有效的 Channel 中取最小的 Watermark；
  3. 保证向下游输入的 Watermark 单调递增；
  4. 排除 IDLE 的 Channel；
  5. 防止刚从 IDLE 恢复，但是 Watermark 落后的 Channel 将整体的 Watermark 拉回去。

Aligned Channel 是指该 Channel 的 Watermark 已经赶上了 Valve 的输出进度，有资格参与最小 Watermark 的计算。一个 Channel 不 Aligned 只有两种情况：

  1. Channel 当前是 IDLE。
  2. Channel 从 IDLE 恢复为 ACTIVE，但是它的 Watermark 还没有追上 lastOutputWatermark。

Channel ACTIVE / IDLE 表示该 Channel 是否还继续产生数据 / Watermark，下游计算 Watermark 时是否要等待它，通过接收上游显式发送 WatermarkStatus.IDLE 或者 WatermarkStatus.ACTIVE 进行判断。最上游的 ACTIVE / IDLE 的判断依据是 WatermarkStrategy.withIdleness(Duration)，当某个 Source 子任务超过指定时间没有收到数据，则将其标记为 IDLE，使其暂时不参与下游 Watermark 的最小值计算。

Channel 与 SubPartition 的关系：在 Flink 中，这两个分别属于生产者侧和消费者侧，是一对多的关系。上游算子的每个并行子任务产出一个 ResultPartition，其中包含多个 ResultSubpartition，每个 ResultSubpartition 对应下游一个消费者（一个 ResultPartition 中的 ResultSubpartition 数量 = 下游消费者数量），数据写入时，根据分区策略（如 Hash、Round-Robin）决定写入哪个 ResultSubpartition。下游算子的每个并行子任务有一个 SingleInputGate，其中包含多个 InputChannel，每个 InputChannel 对应一个上游并行子任务产出的 ResultPartition。流处理模式下，一个 InputChannel 消费一个 ResultSubpartition，是一对一关系，批处理模式下，一个 InputChannel 可以消费多个 ResultSubpartition（通过 ResultSubpartitionIndexSet 指定一个范围），是一对多关系。

其中调用了 OneInputStreamTask.StreamTaskNetworkOutput 的 emitWatermark 方法

其中调用了 AbstractStreamOperator 的 processWatermark 方法

算子先推进当前算子的事件时间计时器（Timer），再向下游发送 Watermark，在 InternalTimerServiceImpl.advanceWatermark 方法中，会找出所有时间小于 Watermark 时间的计时器并依次触发。

Timer 的作用是让某段逻辑在 Watermark 推进到指定事件时间时被触发执行，常见包括

  1. 触发窗口计算；
  2. 用户自定义延迟触发逻辑。

2.5 整体流程

StreamOneInputProcessor.processInput 拉取输入后，AbstractStreamTaskNetworkInput 反序列化出 Watermark，先交给 StatusWatermarkValve 按 Channel 做最小值汇总，只有整体 Watermark 推进时，才通过 StreamTaskNetworkOutput.emitWatermark 调用主算子的 processWatermark，算子收到后推进自己事件时间计时器，触发窗口或用户 Timer，再将 Watermark 传给下游。
