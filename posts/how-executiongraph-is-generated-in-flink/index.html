1.4 Execution

代表 ExecutionVertex 的一次执行尝试，由 ExecutionAttemptID 唯一标识，是一个 Subtask 的实际执行器，ExecutionVertex 在作业的生命周期内通常是静态的（除非改变并行度），但是 Execution 是动态生成的，每当一个子任务因为失败需要重启或因为掉线需要重新调度时，就为对应的 ExecutionVertex 创建一个新的 Execution 实例。Execution 负责生成 TaskDeploymentDescriptor（TDD），它是 JobManager 向 TaskManager 部署 Task 时发送的完整描述信息，其中包含了 TaskManager 启动一个 Task 所需的算子代码、序列化器、配置参数以及上游数据分区的分布信息，通过 RPC 调用，Execution 将 TDD 发送给对应的 TaskManager。包含如下核心字段

为什么要区分 ExecutionVertex 和 Execution？

答：这是一种典型的高可用设计模式，将“任务位置”和“执行过程”解耦。

① 支持重试：若 TaskManager 宕机，ExecutionVertex 依然存在，仅需重新开启一个新的 Execution 尝试即可。

② 历史回溯：ExecutionVertex 可以保留过去多次 Execution 的快照（如失败原因、耗时等），便于进行诊断。

③ 防止脑裂：通过 ExecutionAttemptID，可以拒绝来自“旧的执行实例”的心跳或数据汇报，防止分布式系统中的网络延迟导致的状态错乱。

1.6 EdgeManager

管理所有 Subtask 之间的连接关系，是调度器判断数据依赖的核心数据结构，包含如下核心字段

ConsumedPartitionGroup 是对上游产生的 IntermediateResultPartition 的一组封装，代表一个下游子任务所消费的所有上游分区的集合， ConsumerVertexGroup 是对下游 ExecutionVertex 的一组封装，代表消费同一个 IntermediateResult 的所有下游子任务的集合，它们是调度器用于批量管理数据依赖的分组抽象，避免对每条边单独处理。

二、JobGraph 转换成 ExecutionGraph

在生产环境中，DefaultExecutionGraphBuilder 是唯一的 ExecutionGraph 构建器（其余如 ArchivedExecutionGraphBuilder、CheckpointExecutionGraphBuilder 等均仅作测试用），它是一个纯工具类，通过静态方法 buildGraph 构建 ExecutionGraph。

构建 ExecutionGraph 的核心方法是 attachJobGraph 方法

其中调用了 attachJobVertices 方法构建 ExecutionJobVertex

然后调用 initializeJobVertices 方法，在其中遍历了此前经过拓扑排序的每个 JobVertex，并初始化对应的 ExecutionJobVertex

它首先调用了 VertexInputInfoComputationUtils 工具类的 computeVertexInputInfos 方法，生成了 Map<IntermediateDataSetID, JobVertexInputInfo>，它表示每个 ExecutionVertex 消费上游 IntermediateResultPartition 的范围，用于后续建立上下游连接。

分为两种模式

  1. POINTWISE 模式：上下游 Subtask 之间是局部连接，当上游并行度大于等于下游并行度时，每个下游 Subtask 消费一个或多个上游分区的数据，当上游并行度小于下游并行度，一个上游分区会被多个下游 Subtask 消费，每个下游 Subtask 消费同一个分区中的不同子分区。
  2. ALL_TO_ALL 模式：每个下游 Subtask 都会消费所有上游 Subtask 的数据。

然后再对 ExecutionJobVertex 进行具体的初始化

IntermediateResultPartition 的双重身份：对于上游的 Producer，它是数据的写入终点，Task 运行过程中产生的 StreamRecord 最终会被序列化并存入这个 IRP 对应的 ResultPartition 缓冲区中；对于下游的 Consumer，它是数据的读取起点，下游的 InputGate 会通过网络（Netty）或本地内存访问该 IRP。

注：StreamGraph 和 JobGraph 的生成过程可以通过对 WordCount 程序进行 Debug 来梳理，这两个阶段都在客户端完成，但是生成 ExecutionGraph 的过程在 JobManager 中完成，本地执行 env.exetute() 时会启动一个 MiniCluster，虽然 MiniCluster 在同一个 JVM 中，但是 JobMaster、Dispatcher、Scheduler 在不同的线程中异步启动，因此直接在 buildGraph 方法中打断点无法生效，可以通过运行测试类 DefaultExecutionGraphConstructionTest 的 testExecutionAttemptIdInTwoIdenticalJobsIsNotSame 方法使得在 buildGraph 方法中打的断点生效，因为它直接调用 buildGraph 方法，两者位于同一线程中。
